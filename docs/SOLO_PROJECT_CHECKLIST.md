# 혼자 쓰는 GitHub 프로젝트 체크리스트

작은 프로그램도 **프로젝트 하나에 저장소 하나**, **변경 하나에 작업 브랜치 하나**로 시작합니다. 별도 개발·운영 브랜치를 여러 개 만들기보다 README에 실행법·검사법·배포 조건을 적고, draft PR에서 변경과 검사 결과를 확인한 뒤 반영합니다. 아래는 운영 안내이며 자동배포, 권한, 브랜치 보호 설정을 바꾸지 않습니다.

## 평소 작업: 시작 → 확인 → 반영

- 시작: 현재 브랜치와 미커밋 변경을 확인합니다. 기존 작업을 덮어쓰지 않고 main에서 작업 브랜치를 만듭니다. 진행 중 작업이 있으면 별도 작업공간을 씁니다.
- GPT에 전달: 목표, 수정할 저장소, 보존할 파일, 실행할 검사, 배포 허용 여부를 짧게 적습니다. 기본 요청은 “작업 브랜치와 draft PR까지, main 반영·배포는 별도 지시”로 둡니다.
- 확인: PR의 변경 파일과 diff에서 예상하지 않은 삭제·비밀정보·고객자료가 없는지 보고, README의 검사 명령을 실행합니다. 통과·실패·미실행을 구분해 기록합니다.
- 반영: 배포 조건과 복구 수단을 확인한 뒤 결정합니다. PR 검사가 통과했다는 사실만으로 설치 파일·실제 PC 동작까지 검증됐다고 판단하지 않습니다.

## 새 프로젝트에 복사할 최소 체크리스트

- [ ] 목적·담당자·저장소 공개범위를 정하고 README에 실행 명령, 필요한 버전, 검사 명령, 배포 방법을 적었습니다. 회사 업무·고객 관련 자료는 공개 저장소에 넣기 전에 공유 가능 여부를 확인했습니다.
- [ ] 소스와 필요한 런타임 자산·템플릿·폰트·모델·빌드 설정·테스트·라이선스를 보존하고, 재생성 가능한 build/dist·캐시만 ignore했습니다. 큰 파일도 실행에 필요하면 임의로 지우지 않습니다.
- [ ] API 키·암호는 소스에 적지 않고 로컬 환경변수나 해당 서비스의 비밀정보 설정을 사용합니다. 예제 설정에는 가짜 값만 넣고, 테스트에는 실제 고객자료 대신 익명·합성 자료를 씁니다.
- [ ] 외부 코드·폰트·모델·이미지의 출처와 사용·재배포 조건을 확인하고 필요한 고지·라이선스를 함께 보관했습니다.
- [ ] 작업 브랜치 → draft PR → 검사 → 반영 순서를 정하고, main 반영 또는 태그 생성 등이 배포를 시작하는지 README에 명시했습니다.
- [ ] 버전과 변경 내용을 함께 기록하고, 같은 버전의 공개 설치 파일을 다른 내용으로 덮어쓰지 않습니다. 빌드 성공 외에 핵심 기능·설치·업데이트를 어디까지 확인했는지 기록합니다.
- [ ] 소스 백업과 배포본 복구 수단을 준비했습니다. 중요 변경·정리 전에는 별도 위치에 소스 이력과 필요한 자산, 정상 동작한 배포본·버전·검증 결과를 보관하고 복원 가능한지 확인합니다.

## 실수가 났을 때

비밀키가 올라갔다면 먼저 해당 키를 폐기·재발급합니다. 현재 파일에서 지우거나 ignore에 추가하는 것만으로 과거 커밋에서 사라지지 않습니다. 고객자료 노출은 공유를 멈추고 회사 담당 절차에 따라 처리하며, 이력 삭제·권한 변경 같은 큰 조치는 별도 검토합니다.

잘못된 코드 변경은 원인 커밋을 확인하고 작업 브랜치에서 되돌리는 변경을 만들어 검사합니다. 정상 main을 강제로 과거로 돌리거나 이력을 다시 쓰는 방식은 기본 복구 절차로 쓰지 않습니다. GitHub와 로컬 clone만으로 릴리즈 첨부파일·외부 자산·미커밋 자료까지 백업됐다고 보지 않습니다. 비밀정보 백업은 소스 백업과 분리해 접근을 제한합니다.

## 더뷰어에 적용할 때

현재 실제 절차는 [빌드·검사·배포 안내](BUILD_AND_GITHUB.md)를 따릅니다. `release.yml`의 경로 조건에 해당하는 main push는 자동 빌드·릴리즈 처리를 시작합니다. `release.json`의 `publish`가 true이면 검사 후 공개하므로 main 반영은 배포를 수반할 수 있습니다. 문서만 수정한 경우 등 경로 조건에 해당하지 않는 변경은 같은 동작을 보장하지 않습니다.

릴리즈 workflow의 PR 검사는 소스·설정·안전성 검증이며 Windows 배포 빌드와 공개 job은 실행하지 않습니다. 별도 PDF 회귀 workflow는 해당 경로의 PR에서 테스트용 Windows 패키지를 만들 수 있으므로, 실제 실행된 job과 결과를 확인합니다.

복구 시 정상 버전의 소스와 배포본을 확보하고 변경을 수정한 뒤 **새 버전**으로 배포하는 것을 기본으로 합니다. `pdf_page_dragger.py`의 `APP_VERSION`, `release.json`, 릴리즈 노트를 함께 맞추고, 기존 버전 번호로 되돌린 커밋을 main에 바로 반영하지 않습니다. 같은 버전의 다른 내용은 공개 과정에서 거부될 수 있습니다. 필요하면 보관한 정상 설치 파일로 수동 복구를 검토하되 사용자 문서와 설정을 먼저 백업하고 해당 PC에서 확인합니다.

임시 Actions artifact는 영구 백업이 아닙니다. 더뷰어의 checked distribution은 이 변경이 반영된 뒤 업로드되는 자료부터 7일, 실패 진단·릴리즈 상태는 14일 보관합니다. 보관기간과 별개로 필요한 정상 배포본을 확보해야 합니다.

## 프로젝트가 늘어나면

저장소마다 이 체크리스트와 README의 같은 항목을 사용합니다. 프로젝트 목록에는 저장소 링크·목적·현재 버전·실행/배포 안내 링크만 유지하면 됩니다. 여러 프로젝트를 한 번에 정리하거나 공통 설정을 일괄 변경하기보다 하나에서 확인한 방법을 다음 프로젝트에 적용합니다. 별도 조직·복잡한 승인 체계·공통 배포 시스템은 실제 협업이나 운영 부담이 생겼을 때 추가합니다.
